Lesson 10 — Client Lists & Identity

Update a client list, and manage users with IAM

The fast-path change: edit a list and activate just the list. Then a working tour of Identity & Access Management from the shell.

~20 min Writes — staging first Needs: Lesson 09 Final lesson

Where this sits. Last one. Two skills: updating a client list (the lowest-friction change on the platform — no config version needed) and the basics of IAM (users, roles, groups). Both round out your mission.

The win: a client list with a new, tagged, self-expiring entry active on staging — and an IAM audit you can run against your account today.

Before any write Get-AccountID | Get-AccountName — confirm the account. IAM changes especially: you can lock yourself out.

AUpdate a client list

1 · The change model (recap)

edit the list  →  activate the list  →  done
                  (no security-config version, no property version)

A security policy that references the list picks up the change the moment the list is active. This is why blocklists and allowlists live in client lists rather than in rules.

2 · Add entries

$id = '91_BLOCKABUSE'

# rich entries — value + metadata
$items = @(
    @{ value = '198.51.100.44/32'; description = 'SOC ticket 5099'; tags = @('soc','manual') }
    @{ value = '198.51.100.45/32'; description = 'scraper burst';   tags = @('auto');
       expirationDate = (Get-Date).AddDays(30).ToString('yyyy-MM-ddTHH:mm:ssZ') }
)
Add-ClientListItem -ListID $id -Items $items

# quick shorthand — values only
Add-ClientListItem -ListID $id -Items '203.0.113.10/32,203.0.113.11/32'
Set an expiry on temporary blocks An entry with expirationDate auto-removes itself. Without one, "temporary" blocks become permanent cruft nobody dares delete.

3 · Change or remove an entry

Set-ClientListItem -ListID $id -Value '198.51.100.44/32' `
    -Description 'SOC ticket 5099 - confirmed botnet' -Tags 'soc','confirmed'

Remove-ClientListItem -ListID $id -Value '203.0.113.10/32'

4 · Bulk import from a file

# ips.csv:  value,description,tags,expirationDate
Import-ClientListItem -ListID $id -File .\ips.csv

5 · Check what's pending before you activate

Get-ClientList -ListID $id | Select-Object version, stagingActivationStatus, productionActivationStatus
version stagingActivationStatus productionActivationStatus
------- ----------------------- --------------------------
     56 MODIFIED                MODIFIED

Get-ClientListItem -ListID $id | Where-Object stagingStatus -ne 'ACTIVE' |
    Select-Object value, stagingStatus, description

6 · Activate

$act = New-ClientListActivation -ListID $id -Network STAGING `
    -Comments 'lesson 10 — add SOC + auto blocks' `
    -NotificationRecipients 'you@company.com'

do {
    Start-Sleep 15
    $st = Get-ClientListActivationStatus -ListID $id -Environment STAGING
    "$(Get-Date -Format T)  $($st.activationStatus)"
} while ($st.activationStatus -notin 'ACTIVE','FAILED')
Parameter quirk New-ClientListActivation uses -Network STAGING. Get-ClientListActivationStatus uses -Environment STAGING. Same values, different parameter name — one of the module's few inconsistencies.
Production & allowlists Blocklist production activation is low-risk and fast. Allowlist changes are not: removing an entry from an allowlist that gates access can lock out staff or partners instantly. Stage allowlist changes and verify before -Network PRODUCTION.

BIAM / IDM basics

7 · The model

Identity (user)
   └─ authGrants[]  ──  role  ×  group      "roleId 340 in grp_183544"
API client                                  (Lesson 03 — same grant model)
Role   = a named bundle of permissions
Group  = where the role applies (the access-control tree from Lesson 04)

8 · Read

Get-IAMUser | Select-Object uiIdentityId, firstName, lastName, email, lastLoginDate, isLocked

# one user, with their grants and what you can do to them
Get-IAMUser -UIIdentityID 'B-1-ABC123' -AuthGrants -Actions

# roles, and which you're allowed to grant in a group
Get-IAMRole | Select-Object roleId, roleName
Get-IAMGrantableRole -GroupID grp_183544

# the group tree (IAM view)
Get-IAMGroup | Select-Object groupId, groupName, parentGroupId

9 · Common changes

# create a user with one role in one group, email them a one-time password
$body = @{
    firstName = 'Aiko'; lastName = 'Tanaka'; email = 'aiko.tanaka@company.com'
    country = 'Japan'
    authGrants = @( @{ groupId = 183544; roleId = 340 } )
}
New-IAMUser -Body $body -SendEmail

# update, lock, unlock, remove
Set-IAMUser -UIIdentityID 'B-1-ABC123' -Body @{ jobTitle = 'SOC Lead' }
Lock-IAMUser   -UIIdentityID 'B-1-ABC123'   # suspend access immediately
Unlock-IAMUser -UIIdentityID 'B-1-ABC123'
Remove-IAMUser -UIIdentityID 'B-1-ABC123'
Don't lock yourself out Changing your own authGrants, or locking the account you're authenticated as, can end your session with no way back except another admin. Test grant changes on a low-privilege user first.

10 · An audit you can run today

$users = Get-IAMUser -AuthGrants

# stale: no login in 90+ days
$users | Where-Object { $_.lastLoginDate -and
        [datetime]$_.lastLoginDate -lt (Get-Date).AddDays(-90) } |
    Select-Object email, lastLoginDate

# locked accounts still holding grants
$users | Where-Object isLocked | Select-Object email, isLocked

# never logged in at all
$users | Where-Object { -not $_.lastLoginDate } | Select-Object email, createDate

Try it — one client-list change + one IAM audit

Part A — on a test list, add a tagged, 7-day-expiring entry and activate to staging:

$id = 'YOUR-TEST-LIST'
$item = @{ value = '192.0.2.99/32'; description = 'PS101 lesson 10 test'
           tags = @('ps101'); expirationDate = (Get-Date).AddDays(7).ToString('yyyy-MM-ddTHH:mm:ssZ') }

Add-ClientListItem -ListID $id -Items @($item)
Get-ClientListItem -ListID $id | Where-Object value -eq '192.0.2.99/32'

$act = New-ClientListActivation -ListID $id -Network STAGING `
    -Comments 'PS101 lesson 10' -NotificationRecipients 'you@company.com'
do { Start-Sleep 15
     $st = Get-ClientListActivationStatus -ListID $id -Environment STAGING
     "$(Get-Date -Format T)  $($st.activationStatus)"
} while ($st.activationStatus -notin 'ACTIVE','FAILED')

Part B — run the stale-user and locked-user checks from §10 against your account. Write down how many of each you find.

Show expected results & recovery
  • A: list version bumps, status goes MODIFIED → activation reaches ACTIVE in ~1–3 min (client-list staging is quick). The entry disappears on its own in 7 days.
  • Added the wrong value? Remove-ClientListItem -ListID $id -Value '192.0.2.99/32', re-activate staging. Production untouched.
  • B: most accounts have a few stale users — that's the point of running it. Locked users with live grants are the ones to raise.
  • Get-IAMUser returns nothing → your API client lacks the User Admin grant. Read-only IAM still needs an explicit grant in Control Center.
