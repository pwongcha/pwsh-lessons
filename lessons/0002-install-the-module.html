Akamai · PowerShell 101

Lesson 02 — Setup

Install the Akamai module and prove your environment is ready

Check your PowerShell version, install the module from the PowerShell Gallery, load it, and verify — before you go near a credential.

~10 min No credentials yet Windows 10/11 One-time setup

Where this sits. In Lesson 01 you learned to shape objects. Now you install the toolset. The Akamai PowerShell module is published on the PowerShell Gallery (Microsoft's public module repository) — one command pulls it down. No credentials are involved yet; that is Lesson 03.

The win: Import-Module Akamai succeeds and Get-Command -Module Akamai* lists hundreds of cmdlets. Your machine is now able to talk to Akamai — it just needs keys.

1Check which PowerShell you have

Open PowerShell from the Start menu and run:

$PSVersionTable.PSVersion

Major  Minor  Build  Revision
-----  -----  -----  --------
5      1      19041  4894

The Akamai module needs version 5.1 or higher. Every Windows 10/11 machine ships with Windows PowerShell 5.1, so you are already good to go.

Two different apps, similar names Windows PowerShell 5.1 — blue icon, pre-installed, based on .NET Framework, Windows-only.
PowerShell 7 — black icon, installed separately, faster, cross-platform, actively developed.

Optional: install PowerShell 7

Skip this if you want to keep moving — you can switch later. To install:

winget install --id Microsoft.PowerShell --source winget

Then open “PowerShell 7” (or pwsh) instead of the blue one. The rest of this course works identically in both.

2Prepare the PowerShell Gallery (Windows PowerShell 5.1 only)

By default, Windows PowerShell 5.1 tries to reach the Gallery over an outdated security protocol and fails with Unable to resolve package source. Force modern TLS for this session: 

[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12

If you are on PowerShell 7, you do not need this line.

Make it permanent (optional) Add that line to your profile so you never think about it again: notepad $PROFILE → paste the line → save. New windows will run it automatically.

3Remove the old v1 module if it is there

Akamai PowerShell v2 is a rewrite and cannot coexist with the old AkamaiPowershell (v1) module. Check and remove:

Get-Module AkamaiPowershell -ListAvailable

# if anything is listed:
Uninstall-Module AkamaiPowershell -AllVersions

Nothing listed? Good — you are on a clean machine, move on.

4Install the module

Install the full module. It is a bundle of product submodules (Akamai.Property, Akamai.AppSec, Akamai.IAM, Akamai.Common, and ~15 more) — for this course you want all of them. 

Install-Module Akamai -Scope CurrentUser
  • -Scope CurrentUser installs into your profile — no admin rights needed.
  • First time from the Gallery you will be asked to trust the repository and/or install the NuGet provider — answer Y (or A for “yes to all”).
Later, if you want a smaller footprint You can install one product at a time instead — Install-Module Akamai.Common then Install-Module Akamai.Property. Akamai.Common is always required; it holds the authentication and account plumbing every other submodule depends on.

5Load it and read the warning

Import-Module Akamai

WARNING: The names of some imported commands from the module 'Akamai'
include unapproved verbs that might make them less discoverable...

That warning is expected and harmless — you met it in Lesson 01. Some Akamai cmdlets use verbs like Activate or Purge that are not on PowerShell's approved list. The module works normally.

In PowerShell 7 and recent Install-Module versions, importing is automatic the first time you call any Akamai cmdlet — you may not need Import-Module at all.

6Verify

Get-Module Akamai* | Select-Object Name, Version

Name            Version
----            -------
Akamai.Common   2.x.x
Akamai.Property  2.x.x
Akamai.AppSec   2.x.x
...

Get-Command -Module Akamai* | Measure-Object

Count : 600+

Get-Command *AppSecCustomRule*

CommandType  Name                        Version  Source
-----------  ----                        -------  ------
Function     Get-AppSecCustomRule        2.x.x    Akamai.AppSec
Function     Get-AppSecPolicyCustomRule  2.x.x    Akamai.AppSec
Function     New-AppSecCustomRule        2.x.x    Akamai.AppSec
...

Getting cmdlet names back — even though every real call would fail right now with an authentication error — means the install is done. That error is the subject of Lesson 03.

7Keeping it current

Update-Module Akamai        # pull the latest
Get-InstalledModule Akamai   # what you have now

Check for an update whenever a cmdlet behaves oddly — the module tracks Akamai's APIs and moves quickly.

Try it — the readiness checklist

Run these five in order. Compare each against the expected result. If all five pass, you are ready for Lesson 03.

# 1  $PSVersionTable.PSVersion
# 2  [Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
# 3  Install-Module Akamai -Scope CurrentUser
# 4  Import-Module Akamai
# 5  Get-Command -Module Akamai* | Measure-Object | Select-Object Count
Show expected results & common snags
  • 1 — Major 5 Minor 1 (or Major 7). Anything lower: stop, install PowerShell 7.
  • 2 — no output at all. That is success. (Skip on PowerShell 7.)
  • 3 — a one-time trust prompt, then a progress bar, then back to the prompt.
    “Unable to resolve package source” → you skipped step 2.
    “Administrator rights are required” → you left off -Scope CurrentUser.
  • 4 — the unapproved-verbs WARNING. Expected. Not an error.
  • 5 — Count in the hundreds. If it is 0, the import did not take — close PowerShell, reopen, run Import-Module Akamai again.
